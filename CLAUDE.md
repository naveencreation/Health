## Required workflow

Before implementing any new feature, fixing a bug, refactoring code, or modifying an existing module, first inspect the relevant architecture and documentation. Trace the existing implementation and understand its dependencies before making changes. Follow established project conventions and avoid introducing unnecessary architectural changes.

## What this project is

**Calorify** (Expo slug and npm name `calori`) is an offline-first calorie and health tracker. It covers:
- meal logging: catalog search, custom foods, Open Food Facts barcode lookup, AI food photos
- water, steps (manual and Android Health Connect) and weight/BMI trackers
- analytics reports and local reminder notifications
- a 16-step onboarding that builds a Mifflin-St Jeor calorie plan
- **Ria**, an AI coach that calls Google Gemini directly with the user's own API key (BYOK)

There is no custom backend. The client talks to Firebase Auth, Firestore and Storage directly, and `firestore.rules` / `storage.rules` are the server-side logic.

Stack:
- Expo SDK 57, React Native 0.86 (New Architecture), React 19.2, react-native-web
- TypeScript 6 strict, alias `@/*` → `src/*`
- Reanimated 4, react-native-svg, expo-image, Ionicons
- Firebase JS SDK 12, plus `@react-native-firebase` for Analytics and Crashlytics only
- Jest 29 + jest-expo + Testing Library

Android is the primary target. Web renders inside a 480 px phone frame. The app is light-mode only. `android/` and `ios/` are generated by prebuild (CNG) and gitignored.

- `npm install` runs `scripts/patch-expo-notifications.js` (postinstall). It patches `node_modules/expo-notifications` so Expo Go on Android warns instead of crashing. Installing with `--ignore-scripts` skips the patch.
- `firebase.json` points to `firestore.rules` and `storage.rules`. Deploying the rules is a separate step from shipping the app; deploy them before releasing code that writes new fields.

## Testing requirements

- **Order:** `npx tsc --noEmit` first; run the tests only if it passes.
- **Current state (2026-11-05):**
  - tsc passes.
  - `npm test` runs: 575/576 pass. The one failure is a stale `MarkdownText` snapshot (its styles changed after the snapshot was taken). `TodayBMICard` has been seen to time out under full-suite load.
  - Lint reports 57 errors and 434 warnings. Don't add new ones.
- **Layout:** tests live in co-located `__tests__/` folders.
- **Mocks:** `jest.setup.js` mocks Reanimated (hand-written), AsyncStorage, `firebase/firestore`, and `@/services/firebase` (`auth.currentUser.uid === 'test_user_123'`). `firebase/storage` maps to `src/__mocks__/firebaseStorageMock.js`. If a component needs a Reanimated API the mock lacks, add it to `jest.setup.js`.
- **`NODE_ENV`:** `jest.config.js` forces `NODE_ENV=test`. A global `NODE_ENV=production`, which is common on Windows, makes React drop `act` and breaks Testing Library.
- **What to test:**
  - Put calculations in pure `services/` modules and unit-test them.
  - Any formula change in `*Analytics.ts`, `onboardingCalculator.ts` or `RiaCardParser.ts` needs a test.
  - There are no tests for the sync and hydration effects, the auth flows, `GeminiProvider`, `AIService` or the Firestore rules (no emulator suite). Verify those paths by reading the code.
  - Some existing tests encode known bugs (TD-M21, TD-H9). A failing test after a fix may be the test that's wrong.

## Architecture

### Navigation (no router)
The app has no React Navigation and no expo-router.
- `App.tsx` keeps `activeTab` (`today | tracker | analytics | profile`) in state and mounts only the active tab. Scroll offsets are kept in refs. While the user is unauthenticated or onboarding, `WelcomeScreen` renders in place of the tabs.
- Modals and full-screen tracker sub-screens open through `useOverlay().openModal({ type, ... })` (`src/navigation/OverlayContext.tsx`). The `ActiveModal` union in `src/navigation/types.ts` lists them, and `src/navigation/OverlayHost.tsx` renders them. To add an overlay, add a union member and render it in `OverlayHost`.
  - Only one overlay can be open at a time.
  - Android back closes the overlay; with no overlay open, back returns to the Today tab.
  - The `auth` member is declared but unused. App.tsx runs its own sign-in modal state.
- Nested sub-screens (for example Profile → Goals) use `SlideInSubScreen`, a Reanimated `translateX` layer. The base screen stays mounted.
- Notification taps are routed in `App.tsx` by `content.data.route` (`food_vision`, `water`, `weight`, `today`).

### State, persistence and sync
- **The store.** `HealthProvider` (`src/context/HealthContext.tsx`, about 2.6k lines) is the single store. It owns:
  - auth: Firebase email/password, anonymous, and a local demo guest
  - every mutation (`addMealItem`, `addWater`, `logWeight`, `batchUpdateDailySteps`, …)
  - AsyncStorage persistence
  - Firestore sync and hydration

  It publishes slices that you read with `useAuth`, `useGoals`, `useDailyLog`, `useAnalytics` and `useFoodData` from `@/context`. The `context/{auth,goals,logs,food}/` folders hold only the context objects and types.
- **Offline-first.** Every change writes the whole logs map to AsyncStorage (`@calori_daily_logs_${uid}`, or `_v1` for guests; hydration, `register` and onboarding also mirror a signed-in user's data into `_v1`, TD-H29). After a 1 s debounce, changed dates plus `selectedDate` go to `users/{uid}/dailyLogs/{date}` with `merge:true`. This happens only for signed-in non-guest users, and only once hydration has finished for that uid. Goals go to `users/{uid}`.
- **Hydration does overwrite local data.** For dates that exist in both places:
  - meals and activities take the cloud list when it is non-empty
  - water and steps take the max
  - weight and step entries come from the cloud

  It reads the 90 most recent docs, not 90 days. This is a known data-loss risk (TD-C1). Don't assume local edits survive a re-hydrate. An anonymous guest's history is wiped on the first restart (TD-C2).
- **`firestore.rules` validates every document with `keys().hasOnly([...])` allowlists plus range and list-size caps.** A new field on a synced shape (DailyLog, user root or goals, custom food, chat docs) must be added to the matching validator, or cloud writes fail with "Missing or insufficient permissions" while local saves keep working. Errors are logged only under `__DEV__`.
- **No `undefined`.** Firestore rejects `undefined` values, so run payloads through `sanitizeForFirestore` (`src/services/sync/healthSyncService.ts`).
- **Per-user settings** must use `ScopedStorage` (`src/services/storage/scopedStorage.ts`, `@calori_${uid|guest}_${key}`). Several existing global keys already leak across accounts (TD-M6). Don't add more.
- **Dates** are local `YYYY-MM-DD` strings from `src/utils/dateUtils.ts`, compared as strings. Never build a day key with `toISOString().split('T')[0]`, which gives the UTC date. `selectedDate` and the meal, water and weight mutations clamp future dates; `addSteps`, `addWorkout`, `updateMealQuantity`, `batchUpdateDailySteps` and `updateWeightEntry` do not.
- **Two Firebase SDKs.**
  - The JS `firebase` SDK (`src/services/firebase.ts`) handles Auth, Firestore and Storage.
  - `@react-native-firebase/*` is used only for Analytics and Crashlytics, through `src/services/monitoring.ts`, which lazy-requires them and no-ops in Expo Go, on web and in Jest.
- **SecureStore keys** may contain only `[A-Za-z0-9._-]`. Firebase auth persistence hex-encodes its keys (`fb_auth_<hex>`), and any new SecureStore key must follow the same rule.
- **Defaults.** `src/constants/biometricDefaults.ts` (`BIOMETRIC_DEFAULTS`) is meant to be the single source of fallback goals and targets. Many components still hardcode other numbers (TD-M8). Use the constant and don't add new literals.

### Feature modules
- `src/features/<domain>/` covers hydration, movement, weight, nutrition, onboarding, gamification, subscription, health (Health Connect) and ria (card views).
- The flow within a domain:
  - `hooks/use<Domain>.ts` reads the context slices.
  - `services/*Analytics.ts` holds pure, unit-tested calculations.
  - `components/`, `screens/` and `modals/` render the UI.
  - Each domain exports through `index.ts`.
- Elsewhere: `src/screens/` holds the tab shells, auth screens and profile sub-screens, and `src/components/` holds shared UI.

### Module dependency rules
- Screens and features reach state only through the `@/context` slice hooks or the feature hooks. Never import `HealthContext` internals.
- `src/components/index.ts` re-exports feature components. **Inside a feature, import sibling files by relative path, not from `@/components`**, or you create require cycles.
- The UI calls AI only through `AIService` (`src/services/ai/AIService.ts`). Only `providers/GeminiProvider.ts` touches the network.
- Notification code imports `expo-notifications` only through `src/services/notifications/expoNotifications.ts`.
- Health Connect is reached only through `src/features/health/` and only on Android. Today it is called only from `StepTrackerScreen`.
- Pure `services/` modules must not import React or UI.

### Ria AI coach (`src/services/ai/`)
- **BYOK.** The key is validated with a test call, then stored in SecureStore (`storage/SecureKeyStorage.ts`, key `calorify_gemini_byok_api_key_v1_${uid|guest}`; `localStorage` on web) and sent straight to the Gemini REST API (`providers/GeminiProvider.ts`). The model, limits and token budgets are in `config/AIConfig.ts`, which is authoritative; model names elsewhere are stale. "LangChain" appears only in comments; there is no such dependency.
- **The facade.** `AIService.ts` is what the UI calls (`RiaChatModal`, `FoodVisionModal`, `useRiaDailyInsight`, `BYOKSetupModal`). `errors/AIErrorMapper.ts` maps failures to typed codes, and the UI shows a different recovery action for each code.
- **A chat turn:**
  1. `FastLoopMemoryExtractor` regex-extracts user facts and saves them.
  2. The summary is loaded.
  3. `NutritionContextBuilder` builds the system context (goals, today's log, facts, `MetabolicAdaptiveEngine` TDEE).
  4. The reply streams over SSE.
  5. Once history has 10 or more messages, `ConversationMemoryManager` stores a background summary.
- **Generative UI.** The model emits fenced `ria_action` JSON blocks. `cards/RiaCardParser.ts` strips and validates them: clamps, Atwater consistency (18% tolerance), clinical calorie floors, meal slot by local hour, and a 10-minute duplicate check (`RiaDuplicateChecker`). Views live in `src/features/ria/cards/`. A new card type needs four pieces: the type (`types/ai.types.ts`), the parser regex and builder, the prompt instructions, and a view wired into `RiaActionCard`.

### Notifications (`src/services/notifications/`)
- **Never `import * as Notifications from 'expo-notifications'`.** Its entry point registers push tokens at import time, which crashes Expo Go on Android. Use the `expoNotifications.ts` adapter.
- `engine/planner.ts` is pure. It decides which reminders should exist: meals, water, weight, steps and streak; quiet hours; 30-minute collision priority; a cap of 60.
- `engine/reconciler.ts` diffs that plan against the pending OS notifications by deterministic ID (`calori_<type>_<date>[_slot]`) instead of cancelling everything.
- `App.tsx` calls `NotificationScheduler.syncSchedules` when data or auth changes and when the app returns to the foreground. Android channels are skipped in Expo Go (`src/config/notificationChannels.ts`).

## Implementation rules
- Change behaviour in the layer that owns it: formulas in `services/`, state mutations in `HealthContext.tsx`, overlays in `OverlayHost`. Don't duplicate logic. The repo already has 4 BMR copies, 5 BMI copies and 7 copies of the 0.04 kcal/step factor.
- For any synced shape change, update all of these in one change: the type (`src/types/index.ts`), the payload builder, `sanitizeForFirestore` usage, the rules validator and the hydration merge. See the recipe in DEVELOPMENT_GUIDE §7.
- Keep side effects out of React state updaters in new code. Existing code violates this (TD-M4).
- Check TECHNICAL_DEBT.md before "fixing" odd behaviour; it may be catalogued with an open product question.
- The subscription is a **mock** (`src/services/payments/paymentService.ts`). Don't treat `isPro` as proof of payment.

## Security requirements
- Never copy credentials or config values into code, docs, logs, tests or commit messages. That includes the Firebase values in `.env.example`, the fallback in `src/services/firebase.ts` and `google-services.json`, and users' Gemini keys. Refer to them by file location only. `.env` and `.env.*` are gitignored.
- Treat the Gemini key as a secret: store it only through `SecureKeyStorage`, never log it, display it only with `getMaskedKey`, and never write it to Firestore. A legacy `geminiKeyObfuscated` field is migrated off and deleted.
- Every Firestore and Storage path must stay owner-scoped (`users/{uid}/…`) and pass the `hasOnly` validators; default deny stays at the end of `firestore.rules`. Storage writes are images under 1 MB.
- Guests and `demo_` users must never sync to the cloud. Keep the `isGuest` and `demo_` guards.
- User text sent to Gemini goes through `AIInputValidator` (`src/services/ai/validation/AIInputValidator.ts`), which sanitizes it and wraps it in `<user_untrusted_input>` tags. AI output that writes data goes through `RiaCardParser` clamps and safety floors. Don't bypass either.
- Health data is PII. Keep it out of analytics params and crash logs in new code; existing `Monitoring.logEvent` calls send some values (TD-M7). Per-user local data must use scoped keys.
- Account deletion and logout must clear per-user data. The current gaps are listed as TD-H5 to TD-H7 and TD-H13. Don't "fix" the order by calling `deleteUser` first: the SDK signs out at the end of `delete()`, so later Firestore deletes run unauthenticated. Reauthenticate first (roadmap RM-03).

## UI conventions
Read `DESIGN.md` before UI work. These are the rules broken most often:
- Use tokens from `src/theme/` instead of raw values. Import by subpath: `@/theme/colors` (`Colors`), `@/theme/typography` (`Typography`, `Fonts`), `@/theme/spacing`, `@/theme/icons`, `@/theme/controls`, `@/theme/motion`. The `@/theme` barrel exists but has no importers.
- **Typography:** Urbanist for all UI text and numbers. Kurale only for the "Calorify" wordmark. The Poppins files are bundled but unused.
- **Cards:** 10 px radius with `borderCurve: 'continuous'`, a 1 px hairline border, no drop shadows. On Android, set `elevation: 0` on rounded or circular views, because elevation draws square or octagonal shadow artifacts there.
- **Colour meaning:**
  - calories: primary terracotta `#F47551` (`Colors.primary`)
  - protein: green, which is reserved for it (`Colors.protein`)
  - steps: `Colors.steps` `#F97316`
  - water: `Colors.water`
  - weight: `Colors.weight`

  Never use pure `#000000`.
- **Icons:** Ionicons only for standard actions.
- **Motion:** Reanimated only (no RN `Animated`). Use `withTiming`, not springs, for press feedback. Take durations from `MotionDurations` and curves from `MotionCurves` (`src/theme/motion.ts`). Import `Easing` from `react-native-reanimated`; the RN `Easing` is not a worklet and throws. Respect reduced motion.
- **Components:** `expo-image` for images and `Pressable` for touch targets. Get safe areas from `useSafeAreaInsets`, not hardcoded per-platform padding.
